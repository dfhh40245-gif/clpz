## R01 — P1: pending work escapes the queue bound

Location: `backend/jobs.py:951–957`; task 11.

`_run` releases its admission reservation **before** acquiring `_slots`. Threads waiting for the semaphore disappear from the pending count, allowing more submissions even while all execution slots are occupied. A semaphore bounds active work, not the number of waiting threads.

Reproduction: hold `_slots`, set `MAX_QUEUE_DEPTH=2`, then reserve and start six `_run` workers. **All six were admitted and remained pending, while `queue_depth()` returned 0.** No media work was required for this check.

Required fix: retain reservations while workers wait, or use a bounded queue with a fixed worker pool. Define whether the limit includes active work; release exactly once in the corresponding terminal/dequeue path. Test the real worker-entry path under a held execution slot rather than mocking `try_acquire_slot` to return false.

**Resolution (18 September 2026): fixed.** `MAX_QUEUE_DEPTH` now limits jobs waiting for a worker; active jobs are governed separately by `MAX_CONCURRENT_JOBS`. Reservations are keyed by job ID, remain held until the execution slot is acquired, and are discarded idempotently on cancellation or pre-start failure. Worker slots are released in `finally`. New forge, upload, and retry submissions obey the same pending bound. A held-slot submission test and a real HTTP test with zero workers verify two accepted jobs, a 503 on excess submission before charging, and renewed capacity after cancellation. Completion and failure cleanup have focused tests; see `docs/foundation/evidence/R01-queue-capacity.md`.

## R02 — P1: transcription still has no enforceable hard deadline

Location: `backend/jobs.py:1131–1136`, `backend/pipeline/transcriber.py:transcribe`; task 11.

Whisper remains an in-process synchronous call. The new watchdog handles edit renders; it does not interrupt this call. A model hang can still hold the only job slot indefinitely, despite the reported hard-deadline acceptance.

Reproduction: set `JOB_TIMEOUT_SECONDS=0.05` and inject a controlled blocking transcription function. After 0.25 seconds, **the worker was still alive and the job still transcribing**. The probe then explicitly released the function itself to clean up. This demonstrates that configured expiry alone cannot end the stage.

Required fix: execute uninterruptible heavy stages in a supervised process or equivalent genuinely cancellable boundary. Verify a stuck worker is terminated within deadline plus a stated cleanup tolerance, releases resources, and allows the next queued job to run. Updating status alone is insufficient.

**Resolution (18 September 2026): fixed.** Transcription now runs in a dedicated supervised child process (`transcriber.transcribe_supervised`): the worker thread monitors a `TRANSCRIBE_DEADLINE_SECONDS` hard deadline, force-terminates the child at expiry (terminate→kill), raises `TranscribeTimeoutError` mapped to the distinct `TRANSCRIBE_TIMEOUT` code, and releases the worker slot in `_run`'s `finally`. The parent never loads the model; supervision exchange files are cleaned in all paths. `clpz_server.py` gained `freeze_support()` for frozen-child spawning, and `TRANSCRIBE_SUPERVISED=0` restores the legacy in-process path (used by the hermetic suite). Verified with real child processes: a stuck child (stub blocking 10^6s) is terminated within deadline + 15s tolerance and the job errors `TRANSCRIBE_TIMEOUT`; the queued follow-up job runs to `done` through the same supervision path and the slot is re-acquirable immediately. Full fast suite: 294 passed, 2 skipped, 9 deselected; see `docs/foundation/evidence/R02-transcribe-deadline.md`.

## R03 — P1: the declared persistence authority is not the recovery authority

Locations: `backend/jobs.py:483–513`, `backend/database.py:856–871`, `backend/main.py:1694–1699`; tasks 10 and 18.

`_persist` writes SQLite first and describes JSON as derived, but `load_saved_jobs` restores JSON first and skips SQLite records already present. A crash or snapshot-write failure can therefore restore stale data over a newer committed transaction. In addition, `save_job` does not persist `edit_versions`, so those versions currently rely on the supposedly derived JSON file.

Reproduction: save a done JSON snapshot, commit cancelled state to SQLite, clear in-memory jobs and reload. **SQLite says cancelled; recovered state says done.** Persist a job with an edit version and read it directly from SQLite: **`edit_versions` is absent**.

Required fix: load the authoritative committed store first, migrate/synchronize older snapshots explicitly, and persist edit versions in the authoritative schema. Test divergent snapshots, snapshot failure after a successful DB commit, absent JSON and real restart. A successful `_persist` call plus same-process read is not a durability test.

**Resolution (18 September 2026): fixed.** `load_saved_jobs` restores committed SQLite state only; the JSON snapshot is a derived copy with a single reader (one-time migration v4, guarded against re-running and ghosts). A failed DB read stops startup rather than promoting stale JSON. `edit_versions` is a real column (`jobs.edit_versions`, migration in `backend/database.py`) written by `save_job` and restored by `get_all_jobs`. The review's exact scenarios are tested: SQLite wins over a conflicting done snapshot, snapshot failure after commit still recovers SQLite, recovery without JSON, deleted jobs are not resurrected, and the migration rolls back on failure. See `docs/foundation/evidence/R03-sqlite-authority.md`.

## R04 — P1: upload replay ignores changed file contents

Location: `backend/main.py:1027–1029`, `backend/jobs.py:create_upload_job_idempotent`; task 09.

Replay compares filename/options and returns before reading/fingerprinting the new media. Recording the first file's hash afterward cannot protect the branch that already returned.

Reproduction: generate distinct red and blue MP4 files, upload both as `same.mp4` with the same key/options, and prevent background processing to isolate submission behavior. **Both return HTTP 200 with the same job ID**, instead of rejecting changed content with 409. The actual HTTP upload route and real generated media were used.

Required fix: establish verified content identity before final replay acceptance, using bounded staging/hash computation or an appropriately validated two-phase upload protocol. Test identical replay, changed bytes with unchanged name/size/options, concurrent upload and restart; preserve single charging and clean staging files.

**Resolution (18 September 2026): fixed.** The upload endpoint now stages every
multipart body under the data root, validates it, computes a bounded SHA-256,
and only then claims or reuses an idempotency key. The stored mapping binds the
content digest and request options together. An exact retry reuses the original
job; changed content (including a legacy mapping that cannot prove content
identity) fails closed with HTTP 409. Staging files are removed on success,
replay, validation failure, and exceptions. See
`docs/foundation/evidence/R04-upload-content-identity.md`.

## R05 — P1: direct backend startup has no usable capability token

Location: `backend/capability.py:43–45`, `backend/main.py:_startup_capability_gate`; task 03.

The module consumes a token supplied by desktop launchers, but does not initialize one when starting via the documented direct Uvicorn/server path. `new_token()` exists but is not called during direct startup. With debug off and no launcher token, the UI receives no capability and mutations fail.

Reproduction: import/start the app in a fresh temporary data environment with debug off and `CLPZ_CAPABILITY_TOKEN` absent. **`current_token()` is None; a valid create request receives 403.** This is a direct-start regression; the desktop launchers do generate tokens.

Required fix: initialize the capability securely once for every supported entry point, maintain intended per-launch rotation, and test the actual documented direct-server command and both desktop launch paths. Do not fix this by disabling the gate.

**Resolution (18 September 2026): fixed.** `_startup_capability_gate` now calls `capability.initialize_token()` at import time, so every supported entry point (direct uvicorn, `clpz_server.py serve`, both desktop launchers) has a usable token: an existing launcher token is preserved, a direct start without one generates a fresh local token, and rotation behavior is unchanged. The gate itself is untouched — tests cover preservation, creation, rotation, stale/missing rejection, and that the token never leaks into error text. See `docs/foundation/evidence/R05-direct-start-capability.md`.

## R06 — P1: support bundles are not reliably free of credentials/content

Locations: `scripts/support_bundle.py:34–40`, `scripts/support_bundle.py:146–148`; task 22.

The key/value redaction expression does not match ordinary JSON-quoted keys. Arbitrary error text is also included after only pattern replacement, so the claim that no transcript/user content can appear is too strong.

Reproduction with synthetic values only:

```text
Input: {"password": "synthetic-review-password", "token": "synthetic-review-token"}
Result: both values remain in redact_text output.
Input job error: Transcript: synthetic-private-speech
Result: the full string appears in error_summary.
```

Required fix: prefer explicitly allowlisted structured diagnostic fields and omit free-text content by default. If logs are included, redact structured values correctly and test JSON, headers, multiline text, URL credentials and relevant provider token formats. Do not label arbitrary text safe merely because a few regex tests pass. There is no claim that real customer secrets leaked in this review.

**Resolution (18 September 2026): fixed.** Support bundles now export only a
typed allowlist: machine/tool state, approved environment-setting presence,
job IDs/stages/error codes/timings, and known-log metadata (presence and byte
count). They never export log text, free-form errors, URL/media fields,
transcripts, paths, or unapproved API fields. Text redaction remains a tested
defense-in-depth utility, not the basis for declaring arbitrary user content
safe. See `docs/foundation/evidence/R06-support-bundle-privacy.md`.
